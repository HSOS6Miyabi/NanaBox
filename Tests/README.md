# NanaBox automated tests

The Windows build runs configuration/HCS request self-tests and creates, resizes, compacts, and queries a temporary VHDX using the production disk APIs. `Tests/SettingsUI.ps1` drives the real settings editor through Windows UI Automation: it changes controls, adds/removes GPU, network, disk and share rows, saves a temporary .7b file, checks the serialized values, reloads, and tests the all-GPU mode. The test does not create or start a VM. It requires a Windows desktop session with a working XAML Islands/UI Automation environment.

Run the UI test from Windows PowerShell:

```powershell
powershell.exe -NoProfile -ExecutionPolicy Bypass -File Tests/SettingsUI.ps1 -Executable Output/Binaries/Root/Binaries/x64/NanaBox.exe
```

The packaged executable must have `resources.pri` and its XAML resource file beside it. The editor can also be opened directly using `NanaBox.exe --edit-config path.7b`.

The host-network mutation, GPU-PV, live VM power controls and guest integration tests require a compatible Hyper-V host and disposable test guests. Never run destructive VM/network tests against production VMs or networks.

The settings test executes VHDX creation, expansion, compaction and inspection in the storage page and checks the returned disk sizes. With `-HostIntegration`, it also creates and deletes a uniquely named private Hyper-V switch, registers an isolated Hyper-V firewall creator, configures its policy, creates/disables/enables/deletes a rule, and creates/inspects/deletes an HCN NAT network. Use an elevated, interactive, dedicated Windows Hyper-V runner with NetSecurity's Hyper-V firewall cmdlets available. The manually dispatched hardware workflow enables this mode. External switch creation is not exercised on shared network adapters.

The hardware workflow uses two disposable VM configurations with GPU-PV and mirrored networking enabled, the guest service installed, and a reachable TCP test server. It verifies the exact HCS Running/Paused states, successful HCN synchronization, actual guest GPU identity, a guest address matching a host address, TCP connectivity using a mirrored source address, and clean guest shutdown. The GPU regex inputs must identify the actual expected GPU; for a Linux dxg guest, a pattern such as `"Dxg"\\s*:\\s*true` is accepted. Do not point the workflow at production VMs or network services.

The native self-test also covers atomic configuration replacement, revision conflicts, HCN endpoint ownership, partial network-operation failures, and fault injection at each stage of VM state saving. Production PowerShell scripts (including scripts embedded in C++) are syntax-checked on Windows before building. The settings UI test verifies recovery from a concurrent file edit. The hardware test checks restart, save/restore from the paused state, graceful shutdown and confirmed forced power-off in both disposable guests, including GPU identity and mirrored connectivity after restoration. The guest service workflow also tests IPv4/IPv6 route reconciliation and multiple interfaces in an isolated Linux network namespace.

`Tests/ToolbarUI.ps1` opens the production main-window XAML toolbar with a recording window-command receiver, without creating an HCS VM or an RDP connection. It checks the exact commands generated by every toolbar action, including both toggle states and the power menu. Native self-tests also inject failures into VM stop requests, verifying that failed forced power-off preserves an already pending graceful stop or restart. Hardware integration tests remain necessary for HCS, RDP and physical GPU behavior.

The default SettingsUI run uses a stateful host-management mock for switch, physical adapter, firewall creator, firewall rule and HCN network operations. It exercises XAML controls, confirmation dialogs, request construction, list refresh, state changes, error reporting and recovery. The -HostIntegration switch selects real host APIs instead. Guest queries have a separate injected backend.

The managed HCN network editor supports a default ICS NAT network or a custom JSON creation document. The mock tests use the production settings builder and check preservation of a custom type, schema version, subnet and firewall flag, and rejection of reserved identity properties and host-controlled flow steering. Actual network types and policy support depend on the HCN implementation installed on the host.

The native configuration self-test validates Plan 9 flags, allowed files, manifest generation, hot-add/remove requests, and injected failures in guest unmount, HCS removal and replacement. The guest tests validate mount ownership, default `/media` and custom directories, busy unmounts, inventory refresh and rollback. Windows GUI automation verifies the Plan 9 editor and guest mount operations with a mock backend.

`Tests/DialogsUI.ps1` verifies the exit confirmation choices, About dialog, sponsor actions and message confirmation. External browser and Microsoft Store calls are replaced by injected recording functions, so no real purchase or external navigation occurs during testing.

The Windows GuestTool CI runs an isolated local Bind Filter integration test, including read-only protection, writable mappings, executable image sections, DOS filename reporting, and mapping removal. The hardware workflow additionally requires both guests to enable host GPU driver sharing. It checks the native Windows VSMB mount, all configured Windows share names, GPU restart status and driver inventory, and the Linux read-only WSL driver and library mounts before testing connectivity. The checks run again after restart and restore.

The Windows GPU GuestTool self-test covers initial disabled state, repeated disabled inventories, re-enabling GPU mapping, and retry after an injected cleanup failure. Driver file restoration and link ownership are tested using disposable files.

Virtual SMB inventory tests reject invalid Windows directory components, case-insensitive duplicate names (including Unicode), malformed access flags and writable GPU shares before mounting. The host configuration self-test rejects names that cannot be mounted as Windows directories.

### Linux GTK clipboard input integration

The Linux GuestTool workflow compiles the shared C++ keyboard encoder, checks Unicode scalar conversion and balanced key press/release batches, and exercises a real GTK 3 text entry under Xvfb. The GTK test injects the generated keyboard events using XTest and compares the resulting UTF-8 text. Windows CI tests the host configuration, the keyboard encoder, and the settings control. Actual Hyper-V console transport requires a running VM.

The Windows GuestTool self-test validates Unicode keyboard event encoding, CRLF and tab handling, surrogate pairs, malformed text, active-session selection and default-disabled protocol behavior. The interactive test launches the production input helper, transfers text through the private named pipe, and verifies that the child process inserts the expected text into a real native Windows edit control. Cross-session launch from LocalSystem over Hyper-V sockets requires a running Windows guest.
